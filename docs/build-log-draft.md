# Build log draft (sample, first person)

**What I built.** A local app for people caring for an aging or seriously ill dog or cat. Each day you answer one question, "was today a good day or a bad day?", tick a few behaviors specific to your pet, and optionally score the seven areas of the HHHHHMM quality-of-life scale. Over weeks it shows the trend, flags patterns in careful language, and produces a one-page PDF to bring to the vet. It works end to end: I can add a pet, check in, see the chart, and download the PDF. It's Python and Flask with SQLite, and it runs from a double-click on Windows or Mac.

**How I worked.** I used Claude Code for all of the code. My job was direction: I answered fourteen scoping questions on day one before any code existed, chose Python, chose "offline and one device," and later made the calls that changed the product most: ask one question at a time, make the good-day/bad-day answer the core record, keep it off the internet for now. **What worked, and why.** Refusing to start with code worked. The fourteen answers on the first day meant the language, the clinical scale, and the scope never had to be revisited, and everything after was building, not arguing. Building in milestones with a test run and a commit after each one worked because nothing was ever more than one step from a known-good state. The trend analysis was written as plain functions with no database or web framework in them, so it could be tested with hand-built data. That mattered later. And the thing that worked best was looking at the output instead of trusting tests: screenshots caught a table running off the page, a save button showing on the wrong step, and a wall of thirteen warning boxes; rendering the PDF to an image caught it spilling onto a second page with overlapping labels. None of those would ever fail a unit test.

**What failed.** Loading the chart library from a CDN failed because the environment blocked every CDN; the fix was to pull it from the npm registry and vendor it, which an offline app needed anyway. Deploying to Fly.io from the sandbox failed because Fly's servers were unreachable from it; the workaround was a GitHub Actions workflow that deploys from GitHub's machines, whose first run failed instantly with zero jobs because two lines of shell inside the YAML contained a colon followed by a space, which YAML cannot parse. The first packaged build on GitHub failed because a test-only package had been installed by hand and never written down: a "works on my machine" failure, caught the moment a different machine ran it. And installing Python on my laptop from a remote session is simply impossible, which is why the project ended up with self-contained downloads built on GitHub's Windows and Mac runners.

**Where the model handed me something that looked right and was wrong.** The worst one was in the core feature. The daily check-in has seven sliders that start in the middle. If you didn't touch one and pressed Next, the app saved a 5, as if you'd scored it. Every test passed, because the same model that wrote the code wrote the tests, and both assumed the behavior was correct. It lived for several hours across two design passes and was only caught when I asked for a bug check and it was reconsidered from the user's point of view. The fix gives each slider an "unset" state; only the ones you move are saved. The second was quieter: the baseline form, where you estimate how your pet was six months ago, opened with every category ticked as "unsure," which disabled the sliders, so it saved nothing. The unit tests posted straight to the route and passed. It was caught by a scripted browser walkthrough that clicked through onboarding like a person and then checked whether the dashboard mentioned the baseline. It didn't. Smaller ones: a date format that only works on Linux (caught by re-reading before commit); a PDF helper that passed the same argument twice (caught by fetching every page once); a trend classifier that labeled a single terrible day among steady ones as "increased variability," caught by a test written from one sentence in my spec, "a single bad day is not a trend." Later, a code review of the whole codebase found ten more, three of which were reproduced before fixing: restoring an older backup broke every page, a pet named O'Malley broke the archive confirmation because the name was inside inline JavaScript, and any website open in the same browser could have posted to the app and wiped its data. **What I had to learn that I didn't expect.** That SQLite has no date type and hands you strings unless you tell it otherwise. That the HTML `hidden` attribute loses to any CSS display rule. That a blur effect on a header makes it the anchor for a "fixed" navigation bar, which is why the phone menu stuck to the top of the screen. That YAML has a rule about colons. That a Python function for comparing passwords only accepts plain ASCII. That a program packaged on Linux cannot run on Windows, and that both Windows and macOS warn about any app not signed with a paid developer account. And something less technical: that showing the scale's published threshold as a line on a chart invites people to read it as a verdict, so the app has to label it as the scale's number, never its own.

**What surprised me.** How much the wording mattered. A "safety layer" that refuses certain sentences ("it's time," "you should," "is suffering") changed the product more than any feature, and tests now check that nothing generated can say them. That the most serious bug was in the feature everything depends on, and the tests were part of the problem rather than the solution. That adding a second sample dog with a different trajectory exposed two design flaws within minutes of existing. And how much of "shipping" turned out to be environment rather than code: blocked networks, operating-system-specific builds, code signing, a YAML rule. **Claude Code component.** Everything was built with it. If one piece has to be shown, the trend classifier and its tests: it was written from my spec, got one rule wrong, and the test written from that rule caught it. What Claude Code did for me: asked the questions, wrote the plan, built every milestone, wrote the tests, took and read screenshots, rendered and read PDFs, reviewed its own code and fixed the findings, set up the builds, and kept a dated log of all of it, including this list of its mistakes.
